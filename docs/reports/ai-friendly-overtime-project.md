# AI를 활용해 작은 사내 서비스를 구현할 때의 스택 선택과 검증

## 한 줄 요약

야근 시간을 기록하고 관리자가 월별 현황을 확인·Excel로 내려받는 작은 사내 서비스를 만들었다. 이번 프로젝트에서 얻은 결론은 단순했다. **AI에게 익숙한 표준 스택은 구현 속도를 높이지만, 실제 품질은 사람이 정한 데이터 규칙·권한 경계·테스트에서 결정된다.**

## 만든 서비스와 범위

서비스는 직원과 관리자로 나뉜다. 직원은 야근 기록을 등록·수정·삭제하고 월별 내역을 확인한다. 관리자는 전체 월별 합계, 직원별 집계와 랭킹, 상세 내역을 보고 Excel(.xlsx) 파일을 내려받는다.

기록은 30분 단위로 입력한다. 종료 시각이 시작 시각보다 이르면 다음 날로 처리하므로 `20:00 → 01:00`처럼 자정을 넘는 야근도 입력할 수 있다. 로그인은 별도 가입이 아니라 회사 Google Workspace 계정으로 한다.

## 왜 이 스택을 골랐는가

선택 기준은 유행보다 **작은 팀과 AI가 함께 다루기 쉬운 표준 기술**이었다. 문서, 예제, 문제 해결 사례가 많은 조합일수록 AI가 생성한 코드도 기존 관례에서 크게 벗어나지 않고, 사람이 검토할 위치도 명확해진다.

| 영역      | 선택                            | 이 서비스에 맞는 이유                                        |
| --------- | ------------------------------- | ------------------------------------------------------------ |
| 웹        | React 19 + TypeScript + Vite    | 화면·폼·목록이 중심인 SPA에 익숙한 조합이다.                 |
| 서버 상태 | TanStack Query v5               | 조회·캐시·재요청·로딩/오류 처리를 화면 코드에서 분리한다.    |
| 라우팅    | React Router v7                 | 직원 화면과 관리자 화면을 명확히 나눈다.                     |
| API       | NestJS 11 + TypeORM             | 모듈·컨트롤러·서비스·repository 경계가 분명하다.             |
| 입력 검증 | Nest ValidationPipe + DTO, Zod  | HTTP 요청은 DTO 런타임 검증을, 환경값은 Zod 검증을 사용한다. |
| 인증      | Google ID 토큰 + HTTP-only 세션 | 가입·비밀번호를 만들지 않고 회사 계정을 확인한다.            |
| DB        | PostgreSQL 17                   | 시간 구간 제약, role 분리, 백업·복구를 DB 수준에서 다룬다.   |
| 리포트    | ExcelJS                         | 정산용 `.xlsx`를 만들고 수식 주입을 방어한다.                |
| 배포      | Docker Compose + Caddy          | API·웹·DB를 같은 구성으로 올리고 HTTPS를 단순화한다.         |

여기서 AI 친화적이라는 말은 AI가 정답을 알아서 만든다는 뜻이 아니다. 사람이 이해할 수 있는 기본 구조를 선택해 AI 산출물을 빠르게 읽고, 수정하고, 검증할 수 있다는 뜻에 가깝다.

## AI를 빠르게 쓰기 위한 개발 방식

코드 생성을 바로 요청하기보다, 요구사항을 작게 고정하고 검증 가능한 단위로 나눴다.

1. **설계(spec)** — 사용자 흐름, 예외, 보안 경계를 문서로 정리한다.
2. **계획(plan)** — 변경 파일, 테스트, 실행 순서를 구현 단위로 나눈다.
3. **테스트 선행** — 자정 넘김, 30분 단위, 타인 기록 접근, 시간 중복처럼 실수하기 쉬운 규칙을 먼저 표현한다.
4. **구현·검증** — 작은 변경마다 테스트·lint·build를 실행하고 기능 단위로 커밋을 남긴다.

사람이 집중해서 결정한 부분은 어떤 기술을 쓸지보다 **무엇을 절대 허용하지 않을지**였다. 회사 외 계정 로그인, 타인의 기록 수정, 수식이 실행되는 Excel 셀, 서로 겹치는 야근 기록은 모두 서버나 DB에서 거부해야 한다.

## 실제로 발견한 문제: 동시 야근 기록 중복

처음에는 API가 저장 전에 같은 직원의 겹치는 기록을 조회하도록 만들었다. 일반적인 요청에서는 충분해 보이지만, 두 요청이 거의 동시에 들어오면 둘 다 아직 중복이 없다고 판단한 뒤 저장할 수 있다.

이 문제는 프론트엔드 버튼을 비활성화하거나 API 트랜잭션을 추가하는 것만으로는 완전히 해결되지 않는다. 최종 판단을 PostgreSQL에 맡겨야 한다.

그래서 `overtime_records`에 다음 규칙을 추가했다.

- 같은 직원의 시간 구간은 겹칠 수 없다.
- 시간 구간은 시작을 포함하고 종료를 제외하는 `[start, end)`로 본다.
- 따라서 `18:00–20:00` 다음에 `20:00–22:00`을 기록하는 것은 허용한다.
- DB가 중복을 거부하면 API는 기존과 동일하게 `409 OVERTIME_OVERLAP`을 응답한다.

이 사례는 AI를 이용한 구현에서 사람이 해야 할 검토를 보여 준다. AI는 조회 후 저장이라는 일반적인 패턴을 빠르게 만들 수 있지만, 실제 동시성 규칙을 어디에서 보장할지는 도메인과 DB 동작을 이해한 사람이 결정해야 한다.

## 검증과 운영에서 신경 쓴 점

### 인증과 권한

- Google ID 토큰의 client ID, 이메일 검증 여부, Workspace hosted domain을 서버에서 확인한다.
- 세션 토큰은 JavaScript가 읽을 수 없는 HTTP-only 쿠키로 전달하고 DB에는 해시만 저장한다.
- 관리자 여부는 서버 환경의 허용 이메일 목록으로 판단한다. 화면을 숨기는 것만으로 권한을 판단하지 않는다.

### 데이터와 리포트

- API는 사용자 ID를 클라이언트 입력값으로 받지 않고 로그인 세션에서 얻는다.
- 관리자 Excel은 `.xlsx`로 내려받으며, 사용자 입력이 `=`, `+`, `-`, `@`로 시작하면 작은따옴표를 붙여 수식 실행을 막는다.
- PostgreSQL 계정은 runtime, migration, backup 역할로 나눈다. API 계정에는 schema 변경 권한을 주지 않고, migration은 별도 명령으로 실행한다.

### 배포와 복구

- 운영 DB 포트는 host에 공개하지 않고 Docker 내부 네트워크에서만 사용한다.
- Caddy가 웹 정적 파일과 API 프록시를 제공하고 HTTPS 인증서를 관리한다.
- 백업은 별도 role로 읽고, 임시 DB로 복구하는 절차를 문서와 스크립트로 남겼다.

## 아직 남아 있는 과제

- PostgreSQL E2E는 Docker가 실행되는 환경에서 migration과 동시 요청 회귀 테스트를 반드시 확인해야 한다.
- 현재 기본 `npm test`에는 PostgreSQL을 필요로 하는 SQLite 이관 테스트가 섞여 있다. CI와 로컬 개발자가 같은 방식으로 실행할 수 있게 test command를 분리하거나 DB를 먼저 기동하도록 정리할 필요가 있다.
- 직원 수와 월별 기록이 크게 늘어날 경우 관리자 상세 목록의 pagination, Excel 대용량 생성 방식, 감사 로그와 보존 정책을 추가로 검토해야 한다.

## 다음 프로젝트에 적용할 체크리스트

1. AI가 많이 아는 기술보다 팀이 읽고 고칠 수 있는 표준 구조를 고른다.
2. 입력 검증은 화면만 믿지 않고 API와 DB 경계까지 나눠 둔다.
3. 동시에 두 번 요청되면 어떻게 될지를 기능 요구사항으로 다룬다.
4. 인증·권한·내보내기·백업은 기능이 완성된 뒤의 옵션이 아니라 처음부터 설계한다.
5. AI가 만든 코드도 테스트·migration·운영 문서로 검증 가능한 흔적을 남긴다.

작은 사내 도구일수록 복잡한 플랫폼보다 명확한 규칙과 적은 운영 부담이 중요하다. 이 프로젝트는 그 기준으로 표준 스택을 선택하고, AI가 만든 구현을 사람이 검증하는 과정을 연습한 사례다.
